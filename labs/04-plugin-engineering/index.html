2.Customer brief

Hi — I lead platform engineering at Harbourline. We run two brands, Lumen Home (USD) and Trailhead Supply (EUR), and each brand team runs its own flash sales. Every one of them has re-invented the release checklist: Lumen keeps a three-line skill in a repo of its own, Trailhead pastes a long prompt into each session, and neither checks the things that hurt us last quarter (sale prices stored the wrong way, stock reserved too early, a push to main in the middle of a sale, an on-call engineer with no first-hour procedure).

What I need from you:

  1. One package, shipped once. The flash-sale release checklist and the first-hour incident procedure, installable by any brand team, so every Devin session in the organization gets the same steps.
  2. It must carry more than text. The pricing rule, a guard against pushing to main during a sale, a reviewer that checks a release diff, and the incident tools the incident procedure needs.
  3. Change without chaos. Brand teams will want to tweak it. They must not be able to change what everyone else runs without someone on my team looking at the change first.
  4. Nobody's credentials inside it. The incident tools need a PagerDuty connection. That connection must not live in the package.

You have one two-hour block. My security reviewer signs off before this reaches every session, and she will want a three-minute update at the end.

3.Stakeholders and constraints

  • The security reviewer signs off on anything that runs in every session. She reads files, install screens and approval cards, not prompts. She will ask what runs, where it came from, and who can change it.
  • Brand engineering leads (one per brand) will install it and will want to change thresholds. They do not have admin rights on organization plugins.
  • Me (platform lead) owns main. The planted defects stay in the baseline; any demonstration change goes on a throwaway lab04/* branch and is deleted without merging.
  • Forbidden: real credentials in any file, changes on main, changes to packages/contracts/, and installing at Organization or Enterprise scope before the plugin has been checked at Personal scope.
  • Output: the plugin folder (kept outside the repo or on a throwaway branch), the checker's clean report, a screenshot of the plugin's details panel after install, and a short note for the security reviewer. Keep the note out of commits.

4.Starting state and reset

Run before you start, and again whenever you want the starting state back:

git switch main && git status --short
git branch --list 'lab04/*' | xargs -r git branch -D
rm -rf ~/harbourline-flash-sale ~/harbourline-flash-sale.zip
pnpm lab:reset -- 04

In a Devin session with this repo selected, type @skills:lab-start 04 to run these steps for you, and @skills:lab-cleanup 04 when you finish. From a terminal: pnpm lab:start -- 04 and pnpm lab:cleanup -- 04.

What “clean” looks like

On main with git status --short empty, no local lab04/* branches, no ~/harbourline-flash-sale working folder, and no plugin named harbourline-flash-sale installed at any scope you control (check Customize → Plugins at Personal and Organization). The seed-spec dataset is loaded for both brands.

5.Acceptance criteria

You are done when someone who was not in the room can see each of the following.

  1. One manifest, one name. The plugin folder has .devin-plugin/plugin.json with a lowercase name, and the offline checker (node labs/04-plugin-engineering/solution/plugin-check.mjs --kit <dir>) reports no problems for it.
  2. Both procedures are skills. The release checklist and the incident procedure are separate skills/<name>/SKILL.md files, and after install they appear as two /<plugin>:<skill> commands.
  3. More than text. The same bundle carries at least one always-on or triggered rule, one hooks.json entry, one subagent and one MCP server declaration, and the install preview or details panel lists them.
  4. The guard behaves. With the sale freeze set, the hook refuses a push to main and allows everything else; with the freeze unset it allows the push. Your note says where plugin hooks run and what happens when one fails.
  5. No credentials in the bundle. Every credential in the MCP declaration is a ${NAME} reference. Your note says when and where the connection is made, and who it is shared with.
  6. Installed at Personal scope first. A screenshot shows the plugin installed for you, with the security notice you accepted, before any shared-scope step.
  7. Install routes compared. Your note says, for repository, uploaded .zip and skills-only repository installs: what each can carry, what name it gets, and whether it follows later changes or stays fixed.
  8. Revision predicted, then checked. You wrote down what the installed plugin would contain after the partial revision-2 upload before you checked it, then confirmed with the checker's --revise output or the plugin's version history.
  9. The unauthorised edit goes nowhere on its own. For the brand engineer without edit rights, you show a pending proposal with a diff, the person who must approve it, and the unchanged installed plugin in the meantime.
  10. Inline-secret draft fixed. All three problems in injectors/inline-secret/ are named, and you say what Devin does with each.
  11. Articulation drill completed with the voice coach (section 8), or against a timer offline. The gap report (or self-score) is saved next to your note and not committed.

With fixtures only

Without admin rights or any credentials you still build the whole plugin in a folder, check it with the offline checker until it reports no problems, install it at Personal scope from that folder (zip or repository), and replay the shared-scope moments with the injectors: a skills-only brand repo, a partial revision upload, a plugin with inline secrets, and a brand engineer who is not allowed to edit the shared plugin.

Cannot be exercised without live credentials

  • Connecting a live PagerDuty account to the plugin's MCP server; the reference answer leaves it declared and unconnected
  • Approving a proposed edit from a second, non-admin account; the reference answer replays it from the injector fixture

8.Articulation drill (voice coach)

The coach plays Harbourline's security reviewer. She approves what runs in every session, reads files and approval cards, and asks who can change what.

60-second framing

Lead with what the organization gets, then what is in the box, then what you still need from her. Stems you can use:

  • "Every brand team will run the same checklist because…"
  • "In one install you get…"
  • "What it does not contain is…"

Sinhala-first note: say the outcome first — one package for every team — before naming files or folders.

Think-aloud checkpoint (T+20)

The coach asks what you are looking at and what you will check next. Answer with I see… I think… I'll try… I'll check…. At T+20 you should be choosing how the plugin will be installed and what that choice means later, not polishing the checklist wording.

Think-aloud checkpoint (T+70)

Same four verbs, later in the block. By now a revision or a teammate's change has surprised you. Name the surprise and what you checked. If you need to read the checker output, say "Give me ten seconds to read the checker" rather than going silent.

Three-minute security-reviewer update

Skeleton: What runs → Where it came from → Credentials → Who can change it → What it does not guarantee → Ask. One fact per sentence. Name files and scopes, not features. Pause after each heading word.

Objection round

The reviewer raises one technical and one commercial objection, in character, about 90 seconds each. Reply with: acknowledge → boundary → evidence → offer. The commercial objection needs a number about the brand teams or the upkeep. The objections themselves are not printed here.
