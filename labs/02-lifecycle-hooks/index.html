2.Customer brief

Hi — I'm Priya, the database administrator for Harbourline. Lumen Home and Trailhead Supply share one PostgreSQL database in every environment, and last quarter a well-meaning session ran pnpm db:seed -- --reset against the shared staging database the afternoon before Lamp Week. We lost two days of merchandiser price-list edits for both brands and spent a weekend replaying about 400 orders from the payment provider. Nobody was careless; the command was simply allowed.

We now want Devin working in this repo every day, and I am fine with that on one condition: Devin must never reset or migrate anything except the lab database, and every psql it runs must go through our read-only wrapper. I do not want a paragraph in a README that the agent may or may not read. I want the tool call itself stopped, or quietly rewritten, before it reaches the database, and I want a log that shows me what was stopped and why.

Next week a contractor also proposes a migration that "just relaxes" orders.currency for multi-currency carts. On our side the fulfilment worker reads that column on every new order. If Devin is asked to apply that patch, I expect the policy to refuse it with a reason Devin can read, not to discover it at 2 a.m. when orders stop flowing.

Show me a policy that lives in the repository, that I can review in a pull request, and that I can trust when it breaks: if the policy file itself is wrong, I need to know whether we are locked out or wide open.

3.Stakeholders and constraints

  • In the room: Priya (DBA, the customer), the platform lead who owns .devin/ configuration, and the on-call engineer who will read the audit log during an incident.
  • Forbidden: no change to main — hooks are demonstrated on a throwaway branch only; no schema change; no command may touch any database other than the lab database at localhost:5432/harbourline; do not fix any planted defect in the services.
  • Policy shape: project-level configuration only (.devin/hooks.v1.json plus scripts in the repo); no user-level config, no edits to .devin/config.json permissions.
  • Read-only access: a psql session that Devin opens must be unable to write, even if the SQL it sends is a DELETE.
  • Decision deadline: Priya signs off before the contractor's migration PR is reviewed — end of this session.
  • Budget: one Devin session plus your own verification; no paid integrations.

5.Acceptance criteria

You are done when someone who was not in the room can see each of the following on your throwaway branch, without re-running anything.

  1. The policy is reviewable. .devin/hooks.v1.json on your branch defines a PreToolUse entry for shell commands, a PostToolUse entry and a Stop entry, and every command it runs is a script committed in the repository (not an inline one-liner nobody can read).
  2. Allowed case evidenced. An ordinary command (for example the test suite) and a reset against the lab database both run unchanged; the evidence shows exit 0 and the original input.
  3. Blocked case evidenced. A reset or migration pointed at any other database is denied: the evidence shows exit code 2 and the reason text the agent receives, and the command never ran.
  4. Rewritten case evidenced. A psql command is executed through the read-only wrapper instead of as typed; the evidence shows the original and the rewritten command side by side, and — if PostgreSQL is up — a write attempted through it failing with a read-only error while the row count is unchanged.
  5. Bad migration stopped. After the bad-migration injector, db/migrations/ gains no currency-nullable migration that reached the database, the audit entry names the patch and the reason, and the Stop hook refuses to let the session finish while the file is in the working tree.
  6. Timed-out case evidenced. After the slow-hook injector you record what happened to the tool call (blocked, delayed or allowed), how long it took, and whether that is documented behaviour or something you observed.
  7. Malformed-config case evidenced. After the malformed-hooks injector you record whether the guard still ran, state in one sentence whether the policy fails open or closed in that situation, and name the one change that would make the outcome safe.
  8. Matcher pitfall explained. After the matcher-glob injector you show which tool names the broken matcher guards (if any) and the corrected matcher, with one sentence on the difference between a single pattern and a list of patterns.
  9. Audit trail. One log file lists every allow, block and rewrite decision with a timestamp and the command; it is not committed.
  10. Articulation drill completed with the voice coach (section 8), or against a timer if you work offline. Save the gap report next to your evidence; do not commit it.
  11. Clean exit. main is untouched, the throwaway branch is not merged, and the reset commands in section 4 return the repository to the clean state.

8.Articulation drill (voice coach)

The coach plays Priya, the Harbourline DBA from the brief. It asks one question at a time, times every answer with the shell, stays in character and keeps all feedback for the written report at the end.

60-second framing

Headline first, then one reason, then the proof. Stems you may use:

  • "The risk you described is… It cost you…"
  • "I am putting the policy in… because…"
  • "You will know it works when…"

Sinhala-first note: resist front-loading ("because the reset happened, because the shared database, therefore…"). Say the policy first, then why.

Think-aloud checkpoints (T+15 and T+60)

At T+15 and again at T+60 the coach asks what you are looking at and what you will check next. Answer with the four verbs: I see… I think… I'll try… I'll check…. If you need to read hook output, say "Give me ten seconds to read this" instead of going silent. End on a full stop, not on "…no?".

Three-minute update to the DBA

Skeleton: Outcome → Evidence → Risk → Next action → Ask. One number per sentence (exit codes, seconds, rows). Priya may interrupt twice with a short question; answer it in one sentence and return to the skeleton. Breathe after each heading word.

Objection round

Two objections in character, 90 seconds each, one technical and one commercial; the coach may ask one follow-up if your answer skips the evidence. Reply pattern: acknowledge → boundary → evidence → offer. The objections are not printed here — that is the point.
